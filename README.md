# Система планирования маршрутов доставки

Учебный проект для учёта клиентов, курьеров, заказов, маршрутов и бронирования курьеров на дату. Веб-интерфейс использует Django ORM; консольный интерфейс в `main.py` продолжает работать с исходными JSON-файлами.

## Запуск приложения

Установите Python и откройте PowerShell в корневой папке проекта (там, где находится `manage.py`). При первом запуске выполните:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py import_legacy_data
.\.venv\Scripts\python.exe manage.py runserver
```

Команда `import_legacy_data` нужна **один раз**, только для пустой базы Django. Она перенесёт данные из `data/delivery.sqlite`, а если этого файла нет — из исходных JSON-файлов. Если база уже заполнена, пропустите эту команду: повторный импорт остановится, чтобы не перезаписать данные.

После запуска откройте [http://127.0.0.1:8000/](http://127.0.0.1:8000/). Остановить сервер можно сочетанием `Ctrl+C`. Для последующих запусков достаточно одной команды:

```powershell
.\.venv\Scripts\python.exe manage.py runserver
```

Административная панель находится по адресу [http://127.0.0.1:8000/admin/](http://127.0.0.1:8000/admin/). Если учётной записи администратора ещё нет, создайте её командой `.\.venv\Scripts\python.exe manage.py createsuperuser`.

## Модели и связи

| Модель | Поля и назначение | Связи |
| --- | --- | --- |
| `homepage.Client` | имя, телефон | один клиент — много заказов (`client.orders`) |
| `homepage.Courier` | имя, грузоподъёмность, активность | один курьер — много назначенных заказов и бронирований |
| `delivery_orders.Order` | адрес, вес, статус | обязательный `client`, необязательный `courier` |
| `delivery_routes.Route` | статус и уникальный slug страницы | много заказов через `RouteOrder`; заказ не может входить в два маршрута |
| `delivery_bookings.Booking` | дата и статус `ACTIVE`, `CANCELLED` или `COMPLETED` | обязательные `order` и `courier`; история сохраняется |

Для действующих бронирований действуют частичные уникальные ограничения: один курьер на дату и одна бронь на заказ. `BookingQuerySet` предоставляет методы `active()`, `cancelled()`, `completed()` и `for_date()`. Поиск свободных курьеров исключает только бронирования со статусом `ACTIVE`, проверяет активность курьера и грузоподъёмность. Маршрут получает курьера из связанных заказов; `RouteOrder.clean()` не разрешает включить заказ без курьера или смешать курьеров в одном маршруте.

## Данные и миграция с предыдущей работы

Текущая база Django — `db.sqlite3` (файл не хранится в Git; для изолированных проверок путь можно задать через `DJANGO_DB_PATH`). Прежняя предметная база `data/delivery.sqlite` остаётся на месте как источник переноса и для демонстрации практической работы с прямым SQL. Команда `import_legacy_data` читает из неё клиентов, курьеров, заказы, связи маршрутов и **все бронирования, включая отменённые**. При переносе прежний `is_cancelled` преобразуется в статус `CANCELLED` или `ACTIVE`. Если файла нет, команда загружает четыре исходных `data/*.json`; в этом случае бронирований в источнике нет. Данные копируются в одной транзакции. Команда отказывается перезаписывать уже заполненные ORM-таблицы.

Миграции ПР10 отдельно добавляют поле `status`, переносят значения из `is_cancelled` и удаляют старое поле. Для существующих маршрутов миграция заполняет slug (`marshrut-<id>`). Исходные записи остаются доступными после применения миграций.

Для переноса из другого файла: `python manage.py import_legacy_data --source путь/к/старой.sqlite`. Если ORM-таблицы уже заполнены, команду повторять не требуется. Исходные JSON, прежняя SQLite и консольные сценарии не меняются при работе сайта. При новом развёртывании из Git, где SQLite отсутствует, импорт берёт исходные JSON.

## Страницы

| URL | Сценарий |
| --- | --- |
| `/` | фактические количества клиентов, курьеров, заказов и маршрутов |
| `/orders/` | поиск по адресу, клиенту и курьеру, фильтр по статусу, пагинация |
| `/orders/<id>/` | детали заказа, клиент, курьер, действующая бронь |
| `/routes/`, `/routes/by-slug/<slug>/` | маршруты и подробная страница по slug; старый `/routes/<id>/` сохранён |
| `/bookings/available/` | поиск свободных курьеров на дату и по весу заказа; переход к форме создания |
| `/bookings/`, `/bookings/<id>/` | фильтрация по статусу, дате, курьеру и заказу, сортировка, пагинация и детали |
| `/bookings/create/`, `/bookings/<id>/edit/` | создание и редактирование через Django ModelForm |
| `/bookings/<id>/cancel/` | отмена действующей брони только через POST |
| `/statistics/` | показатели, группировка заказов, нагрузка курьеров и бронирования |

Представления в `homepage/`, `delivery_orders/`, `delivery_routes/` и `delivery_bookings/` обращаются к моделям Django. Они передают данные в существующие шаблоны через контекст. Общая навигация получает название сайта и число курьеров через `homepage.context_processors.site_navigation`. Для отсутствующих заказов, маршрутов, бронирований и URL возвращается HTTP 404.

Фильтры бронирований описаны в `BookingFilterForm` (`forms.Form`): GET-параметры проходят `is_valid()` перед применением к QuerySet, а сортировка и пагинация сохраняются. Создание и редактирование выполняет `BookingForm` (`forms.ModelForm`); она проверяет дату, статус заказа, активность и грузоподъёмность курьера, а также конфликты действующих бронирований. При редактировании текущая запись исключается из проверки конфликтов. Ошибки выводятся рядом с полями с сохранением введённых значений. Изменения данных выполняются POST-запросами с CSRF-токеном; при отмене запись остаётся в истории со статусом `CANCELLED`. Подробная проверка — в [указателе ПР11](docs/pr11_checklist.md).

## Django Admin и отладка

Модели зарегистрированы в `/admin/` с русскими названиями, столбцами, поиском, фильтрами, сортировкой и встроенными формами бронирований у заказов и курьеров. Для входа создайте локального администратора командой `python manage.py createsuperuser`. Django Debug Toolbar подключается только при `DJANGO_DEBUG=1`; в локальном браузере откройте вкладку **SQL** на страницах бронирований и сравните запросы списка, фильтров и деталей. При `DJANGO_DEBUG=0` панель отключена. Подробная проверка — в [указателе ПР10](docs/pr10_checklist.md).

## Проверки

```powershell
python manage.py makemigrations --check --dry-run
python manage.py showmigrations
python manage.py check
python -m pytest -q
python -m flake8 .
```

Тесты `tests/test_orm.py` проверяют связанные объекты, запрет смешанных маршрутов, создание и отмену брони, освобождение курьера и ограничение уникальности. Веб-тесты проверяют страницы, поиск, фильтр, пагинацию, статистику, 404 и пользовательский путь бронирования. [Указатель ПР9](docs/pr9_orm_checklist.md) содержит команды проверки и 15 ORM-выражений для демонстрации. Исходные SQL-сценарии и их тесты сохранены как материал предыдущей практической работы; они больше не обслуживают Django-страницы. Для их демонстрации см. [чек-лист ПР7](docs/pr7_checklist.md) и [вопросы оценивания](docs/pr7_grading_7_6.md).

Настройка PyCharm описана в [docs/pycharm_setup.md](docs/pycharm_setup.md).
